## 설치 경로와 호스트 연결

PLUGIN_ROOT는 이 진입점이 속한 설치 플러그인 루트다. skills/<id>/SKILL.md에서는 ../..이다. 공용 scripts/assets/tmpa는 플러그인 루트에 한 번만 배치한다. 스킬의 references와 보조 문서는 해당 스킬 파일 기준이다.

`${PLUGIN_ROOT}`와 `${PLUGIN_DATA}`가 셸에 자동 설정됐다고 가정하지 않는다. 로드한 파일의 실제 위치로 루트를 확인하고, 실행할 때 실제 절대경로로 대체하거나 동일 셸 호출에서 변수를 설정한다. PLUGIN_DATA는 호스트가 제공하는 영속 데이터 경로를 우선 사용하고, 없으면 사용자 데이터 디렉터리 아래 이 플러그인 전용 경로를 사용한다. 사용자의 분석 대상 작업 디렉터리는 바꾸지 않는다. bash 예제는 bash에서 실행한다.

SKILL_ROOT는 지금 읽은 SKILL.md의 부모 디렉터리다. 이 스킬 전용 scripts/assets는 SKILL_ROOT 아래에 있다. `${SKILL_ROOT}`는 설명용 표기이며 자동 설정된 환경변수가 아니다. 스크립트 실행 시 로드한 SKILL.md의 실제 위치로 절대경로를 구성한다. 프로젝트 작업 디렉터리를 스킬 폴더로 바꾸지 않는다.

# COVER EE 커버리지 수집

## 스킬 파일 경로

실행 코드와 배포 JAR는 이 `SKILL.md` 옆의 `scripts/`, `assets/plugin/`에 있다.
`${SKILL_ROOT}`는 이 파일이 설치된 실제 디렉터리이며 자동 설정되는 환경변수가 아니다. 실행 예제의 경로를 이 파일 위치 기준 절대경로로 바꾸고 공백이 있으면 따옴표로 감싼다. 분석 대상 프로젝트의 작업 디렉터리는 바꾸지 않는다.
주 진입점은 [수집 클라이언트](scripts/cover_cdt_collect.py), [IDE 플러그인 설치기](scripts/install_cdt_plugin.py), [덤프 검증·전달](scripts/cover_stm32_dump.py)다. 아래에 파일명만 적힌 명령도 이 스킬의 `scripts/`에서 찾는다.

## 범위와 현재 구현 상태

사용자가 기존 IDE에서 테스트한 뒤 수집을 요청하면 해당 실행의 메모리를 수집한다. 커버리지 빌드와 독립된 스킬이며 수동으로 계측 빌드한 프로젝트에도 사용한다. 빌드 스킬 설치 여부나 이전 빌드 기록을 필수 조건으로 요구하지 않는다.

자동 수집은 포함된 Eclipse CDT 플러그인을 통해 기존 IDE Debug 세션을 사용한다. Java 플러그인 소스와 빌드 설정은 `plugin/`, 배포 JAR는 `assets/plugin/`, Python 클라이언트는 `scripts/cover_cdt_collect.py`에 있다. 스킬과 플러그인을 같은 저장소에서 관리한다. 설치와 명령은 [CDT 연동](references/stm32-cdt.md), 개발 방법은 [플러그인 개발](plugin/README.md)을 따른다.

사용자는 IDE에서 원하는 테스트를 수행한 뒤 “커버리지 데이터 측정해줘”라고 요청한다. 플러그인이 설치되어 있고 대상 세션이 하나로 정해지면, 스크립트가 정지·덤프·검증·Agent 전달까지 수행한다. 사용자가 GDB 명령이나 Export 크기를 입력할 필요는 없다. 테스트를 끝냈다는 요청이 명확하면 같은 확인을 반복해서 묻지 않는다.

플러그인이 없으면 최초 설치와 IDE 재시작이 필요하다. 현재 RAM 데이터를 보존해야 하는지 확인하기 전에는 IDE를 종료하지 않는다. 자동 수집을 준비할 수 없으면 `수집 결과: 대기`로 보고하고, 사용자가 수동 대안을 선택한 경우에만 [수동 GDB 절차](references/stm32-gdb-manual.md)를 따른다. GUI 제어나 두 번째 GDB 연결로 임의 전환하지 않는다. JAR 빌드·설치·모의 테스트 성공과 실제 보드 수집 성공은 구분한다.

## 시작할 때 확인할 내용

IDE 버전 호환성을 확인할 때는 [호환성 조사와 검증 기준](references/ide-compatibility.md)을 따른다. 설치기의 `status`는 현재 Java와 등록 번들 정보를 함께 출력한다. 공식 제품 구성표, API 컴파일 성공, 실제 보드 수집 성공을 구분한다. 개발용 Java 11 후보가 준비됐다는 이유로 기존 배포 JAR나 설치 제한을 임의로 교체하지 않는다.

- 사용자가 테스트를 마쳤고 이번 데이터를 수집하려는지 확인한다. 테스트 시나리오를 추측해 실행하지 않는다.
- 먼저 `cover_cdt_collect.py doctor --project <프로젝트>`로 실행 중인 IDE·작업 공간 후보와 접근 상태를 조사한다. 사용자가 작업 공간을 주었다면 앞에 `--workspace <경로>`를 전달한다. 후보가 하나면 사용하고 여러 개이거나 프로세스 조회가 제한되면 필요한 경로만 질문한다. 프로젝트 폴더와 IDE 작업 공간은 같다고 가정하지 않는다.
- Agent 설치 경로는 `CODESCROLL_TM_INSTALL_PATH`에서 읽고 없으면 요청한다. 기본 감시 경로는 설치 루트의 `coverage`이며 고객 설정이 다르면 확인한 절대 경로를 `--monitoring-path`로 전달한다. 별도 Java를 사용하면 `--java-path`로 지정한다. Agent 설정 자체를 변경하거나 감시 폴더의 부모를 설치 루트로 추측하지 않는다. `doctor`는 서버에서 감시 설정을 조회하지 않으므로 이 값의 확인은 별도 절차다.
- `.cover-ee` 기록이 있으면 경로 확인에 참고하되 현재 ELF·Debug 세션과 대조한다. 기록이 없다는 이유로 다시 빌드하지 않는다.
- 로컬 덤프와 파일 전달에는 COVER Access Key나 Open API 포트를 요청하지 않는다. 이 스킬에는 서버 조회 단계가 없다.

## 수집과 검증

1. 현재 Debug 세션과 ELF를 확인한다. 심볼 파일이 같아도 실제 보드 펌웨어가 같은지는 별도 확인이 필요하다.
2. 사용자가 실행한 펌웨어의 런타임 초기화와 테스트가 이미 끝난 상태에서 자동 수집 클라이언트를 실행한다. 플러그인이 정지 전에 프로세스·실행 컨텍스트 수를 확인하고, 지원하는 대상만 정지해 메모리를 읽는다. 초기화를 위해 프로그램을 다시 실행하지 않는다. 현재는 단일 프로세스/코어·단일 실행 컨텍스트를 지원한다. `sdump_buf`의 배열 여부·정수/문자 요소·요소 크기 1바이트·전체 크기를 CDT에서 확인한다. typedef 표시 이름만으로 거부하지 않지만 포인터·알 수 없는 타입은 실패 처리한다. `cv_data`, `cv_size` 등을 대체 버퍼로 추측하지 않는다.
3. Agent 감시 폴더 밖에 Raw Binary를 저장한다. 배열의 남는 공간을 임의로 잘라내거나 바이트를 변경하지 않는다. 스크립트가 세션·ELF·배열 크기·덤프 해시를 대조한다. 읽는 중 타깃이 재개되거나 ELF가 변경되면 전달하지 않는다.
4. 설치된 Agent의 Java로 `bin/cover-cvd-utility.jar -m VIEW -i <덤프 파일>`을 실행한다. 공통 구현은 `scripts/cover_stm32_dump.py`를 사용한다.
5. 검증 종료 코드가 0일 때만 확인한 Agent 감시 폴더에 전달한다. 완성된 파일만 노출하도록 `.partial` 작성 후 `.cvd`로 이름을 바꾼다. 전달 전후 상태는 `delivery.json`에 기록한다.
6. 수집 후에도 타깃을 정지 상태로 둔다. 파일 크기·해시·검증 로그·전달 경로를 보고한다.

덤프가 작업 폴더에 보존된 뒤 검증·전달만 실패했으면 `resume --capture-dir <수집 폴더>`로 재개한다. 이 명령은 IDE에 접속하지 않는다. `DELIVERY_UNCERTAIN`이면 Agent가 파일을 이미 처리했을 수 있으므로 재전달하지 않고 전달 기록과 Agent 상태를 확인한다. 실패 후 보존된 덤프를 무시하고 다시 수집하지 않는다.

고객 IDE에 플러그인을 배포할 때는 설치기의 `status`로 상태를 확인한다. 기존 설치가 있으면 알려진 배포본인지 확인한 뒤 `--action update --ide-closed`로 교체한다. 제거와 백업 복구도 같은 설치기의 `remove`, `rollback`을 사용하며, 실행 중인 IDE를 강제 종료하지 않는다. 최초 배포 버전은 `0.0.1`, 프로토콜은 `1`이다. 현재 Python은 두 값이 모두 일치해야 연결한다. 등록된 버전이나 JAR 해시를 확인할 수 없으면 임의로 덮어쓰거나 제거하지 않고 중단한다. 교체 전 사용자 테스트 데이터를 보존하고, 스킬을 갱신했다고 IDE 설치본도 자동으로 바뀌었다고 가정하지 않는다.

## 변경하지 않는 항목

- 원본 빌드, wrapper 설정, 툴체인 매핑을 변경하지 않는다.
- 펌웨어 재다운로드, reset·load·자동 resume을 수행하지 않는다.
- Agent 감시 경로에 넣으면 서버 업로드가 시작될 수 있으므로 전달 대상을 현재 요청의 Agent로 한정한다.
- 최초 플러그인 설치는 수집과 구분한다. 현재 RAM 데이터를 보존해야 하는지 확인하기 전에 IDE를 종료하거나 재시작하지 않는다.
- 정지·읽기 시간 초과 시 명령이 아직 처리 중일 수 있으므로 자동 재시도하지 않는다. 현재 IDE 상태를 먼저 확인한다.
- 자동 수집은 공백·한글이 있는 작업 경로를 사용할 수 있다. 수동 GDB 대안만 덤프 작업 경로의 공백·따옴표를 제한한다.

## 결과 보고

첫 줄에 `수집 결과: 성공`, `수집 결과: 실패`, `수집 결과: 대기` 중 하나를 표시한다. 이어서 다음을 짧게 보고한다.

- 메모리 덤프, CVD 검증, Agent 전달의 개별 결과
- 대상 프로젝트·ELF·Debug 세션과 타깃 정지 상태
- 덤프와 검증 로그의 절대 경로, 파일 크기, 전달 경로
- 실패·대기이면 중단 이유와 다음에 필요한 조치

`CVD_PUBLISHED`는 검증된 파일을 Agent에 전달했다는 뜻이다. 서버 반영, 커버리지 수치, 테스트 충분성까지 성공했다고 보고하지 않는다. 현재 `serverMeasurementVerified`는 `false`이며 서버 확인은 구현 범위 밖이다.
