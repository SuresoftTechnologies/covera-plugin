# STM32 수동 GDB 덤프 보조 절차

사용자는 STM32CubeIDE에서 Debug로 실행하고 원하는 테스트를 수행한다. 테스트를 마친 뒤 기존 디버그 세션을 Suspend하고 아래 스크립트로 메모리를 내보낸다. 이 기능은 커버리지 빌드와 별도로 요청했을 때 사용한다.

이 수동 보조 도구는 GDB 명령 생성, CVD 구조 검증, Agent 감시 경로 전달까지 담당한다. IDE 콘솔 자동 선택과 타깃 자동 정지는 하지 않는다. 자동 수집은 별도 [CDT 연동](stm32-cdt.md)을 사용한다. 어느 방식이든 Agent 업로드 완료 및 서버 측정 결과는 확인하지 않으며, 파일 전달만으로 측정 전체 성공을 선언하지 않는다.

## 준비

GDB의 Python 지원 여부는 IDE 설치본에 따라 다르다. 이 절차는 GDB 기본 명령으로 덤프하고 외부 Python에서 파일을 검증하므로 GDB 내부 Python 지원을 요구하지 않는다.

1. 디버깅에 사용한 ELF의 절대 경로를 확인한다. 실행 중인 펌웨어를 다시 빌드하거나 내려받지 않는다.
2. 다음 명령으로 작업별 덤프 스크립트를 만든다. 경로는 현재 환경의 실제 값으로 지정한다.

```text
python "${SKILL_ROOT}/scripts/cover_stm32_dump.py" prepare
  --work-dir <프로젝트 경로>/.cover-ee/measurements
  --elf <현재 디버깅 ELF 경로>
  --agent-dir <COVER Agent 설치 경로>
```

`--agent-dir`를 생략하면 `CODESCROLL_TM_INSTALL_PATH`를 사용한다. 감시 경로는 해당 설치본의 `coverage`이며 실제 Agent 감시 설정이 이 경로인지 확인한 뒤 사용한다. 준비 작업은 타깃이나 Agent에 연결하지 않는다.

현재 초안의 `--work-dir`는 공백과 따옴표가 없는 절대 경로를 사용한다. STM32 GDB의 `dump` 명령은 따옴표로 묶은 파일명을 일반 셸과 같은 방식으로 처리하지 않는다. 프로젝트 경로에 공백이 있으면 덤프 작업 디렉터리만 공백 없는 별도 경로로 지정한다. ELF와 Agent 경로에는 이 제한이 없다.

## IDE에서 덤프

1. 테스트가 끝나면 IDE에서 해당 타깃을 Suspend하고 정지 상태를 확인한다.
2. 해당 세션의 GDB 콘솔에서 `info files`를 실행해 준비 명령에 전달한 ELF와 일치하는지 확인한다. 현재 구현은 타깃 펌웨어와 ELF의 일치를 자동 증명하지 않으므로 이 확인을 생략하지 않는다.
3. 준비 명령이 출력한 `gdbCommand`를 같은 콘솔에서 실행한다.
4. `COVER_DUMP_SAVED`와 오류가 없는지 확인한다. 덤프 후 타깃은 정지 상태로 둔다.

이때 실행 중인 프로그램은 해당 ELF로 다운로드한 계측 펌웨어여야 한다. `info files`는 GDB가 참조하는 심벌 파일만 확인하므로 보드 펌웨어와의 일치까지 증명하지 않는다. 세션을 시작한 뒤 다른 프로그램을 다운로드했다면 먼저 세션과 펌웨어 관계를 확인한다. 형식 검증은 버퍼 내용이 완전한 측정이라는 증명이 아니며 초기화 중간에 정지한 경우 실패할 수 있다.

생성된 명령은 `dump binary value`로 `sdump_buf` 값 전체를 Raw Binary로 저장한다. 배열이라면 배열 전체 크기가 적용되며 주소나 배열 크기는 고정하지 않는다. 수동 스크립트는 배열 타입을 강제 검사하지 않으므로 실행 전에 GDB의 `ptype sdump_buf`로 char 배열인지 확인한다. 포인터이거나 타입을 알 수 없으면 진행하지 않는다. 심볼이나 크기를 확인할 수 없을 때 다른 버퍼나 숫자를 추측하지 않는다. 이 버퍼를 사용하는 런타임이 초기화되어 있어야 한다.

자동 수집은 Eclipse CDT 플러그인을 사용한다. 이 문서는 플러그인을 사용할 수 없을 때 사용자가 선택하는 수동 대안이며, GUI 자동 제어를 기본 방식으로 사용하지 않는다. 외부에서 두 번째 GDB를 연결하거나 reset, load, continue 명령을 실행하지 않는다.

## 검증 및 전달

```text
python "${SKILL_ROOT}/scripts/cover_stm32_dump.py" publish
  --capture-dir <prepare가 출력한 captureDirectory>
```

원래 배열의 남는 공간을 포함한 파일 바이트를 그대로 보존한다. CVD 형식은 스크립트에서 직접 해석하지 않고 Agent 설치본의 Java로 다음 제품 검증 도구를 실행한다.

```text
<Agent>/jre/bin/java -jar <Agent>/bin/cover-cvd-utility.jar -m VIEW -i <덤프 파일>
```

Windows에서는 `java.exe`를 사용한다. 제품은 정상 검증 시 종료 코드 0을 반환하고, 검증 실패 시 오류 코드를 반환한다. 출력은 작업 디렉터리의 `cvd-view.log`에 기록한다. 종료 코드가 0일 때만 파일을 전달하며, 실행 오류나 60초 시간 초과는 실패로 처리한다. 준비 이후 ELF 또는 검증 중 덤프 파일이 변경됐으면 전달하지 않는다.

검증된 파일은 `coverage` 디렉터리의 `.partial` 파일로 먼저 기록한 뒤 같은 디렉터리에서 `.cvd`로 이름을 변경한다. Agent가 작성 중인 `.cvd`를 읽는 일을 피하기 위한 순서다. 작업 디렉터리의 `memory.bin`은 증거로 유지한다.

결과는 `result.json`에 파일 크기, 해시, 검증 도구·종료 코드·로그 경로, 목적지와 `CVD_PUBLISHED`로 기록한다. 이는 파일 전달 성공이며 서버 측정 결과 확인은 아니다. `serverMeasurementVerified`는 현재 구현에서 항상 `false`다. Agent가 파일을 바로 이동하거나 삭제할 수 있으므로 목적지 파일이 사라졌다는 이유만으로 실패 또는 업로드 성공을 판정하지 않는다.
