# 실행 시간 최적화 원칙

빌드 결과를 확인하는 근거는 유지하며 같은 사실을 반복해서 확인하지 않는다. 이 원칙은 Visual Studio, GCC/CMake/Make, STM32CubeIDE, C#, Java에 공통으로 적용한다.

## 공통

재사용은 두 경우를 구분한다. 같은 작업을 재개할 때에는 입력이 같은 성공 단계를 이어 쓰고, 새 작업에서는 이전의 환경조사 결과만 재사용한다. 새 작업의 원본 빌드와 계측 검증을 과거 결과로 대체하지 않는다.

- 새 작업에서는 `project_index.py`로 프로젝트 파일 목록을 만들고 `project-index.json`을 네이티브·STM32CubeIDE·C#/Java 탐지에 공유한다. 같은 작업을 재개할 때에는 기존 목록과 입력 확인 기록을 비교한다. 관련 파일의 내용과 디렉터리별 파일 목록이 같으면 인덱스 생성과 탐지를 반복하지 않는다. 새 소스나 빌드 파일을 놓치지 않도록 입력 확인을 위한 디렉터리 열거와 해시 계산은 계속 수행한다.
- 여러 모델 판단이 필요하면 빌드 진입점·구성·타깃·도구 선택을 한 묶음으로 제시하고 한 번에 결정한다. 앞 단계 하나를 고른 뒤 같은 파일을 다시 읽어 다음 질문을 만드는 식으로 왕복하지 않는다.
- 같은 `job.json`을 재개할 때 이미 성공한 단계의 JSON과 입력 식별값이 일치하면 그 단계를 재사용한다. 관련 프로젝트 파일·명령·환경 초기화 근거가 바뀐 경우에만 해당 단계부터 다시 수행한다.
- 성공 단계 기록을 재사용할 때에는 내용 해시로 빌드 설정 파일의 변경 여부를 확인한다. 이후 빌드에 유지하는 COVER 연결을 동일 바이트로 해제·복원하면서 수정 시각만 바뀐 경우나, 인증 입력 방식·프롬프트 옵션만 바뀐 경우에는 성공한 원본 빌드를 무효화하지 않는다. 소스·빌드 정의·원본 명령·구성·도구가 실제로 바뀐 경우에는 다시 수행한다.
- `COVERAGE_BUILD_VERIFIED`로 끝난 다른 작업은 실행 결과 전체를 재사용하지 않고 `.cover-build/cache/environment-profile.json`에 저장한 빌드 환경 프로필만 재사용한다. 프로필 스키마·버전, 프로젝트 절대 경로, 현재 타깃·산출물·generator·빌드 구성 요청과 기존 선택, 빌드 설정 파일 목록·해시, 실제 도구 식별 정보가 모두 일치해야 한다.
- 환경 프로필이 일치하면 이전 프로젝트 파일 목록, 언어·빌드 시스템 판정, 진입점·구성·타깃·프레임워크·goal·task 선택과 구조화된 원본 명령 후보를 불러온다. 소스 파일만 변경된 경우에는 환경조사를 반복하지 않지만 현재 작업의 원본 빌드(상세 로그 포함)는 다시 수행한다.
- 최초 커버리지 빌드 요청에 Access Key가 없으면 채팅으로 한 번 요청하되, 원본 빌드와 실제 툴체인 확인 뒤 첫 Open API 작업 전까지 사용하지 않는다. 받은 값은 현재 대화·실행기 프로세스 메모리에서만 재사용하며 파일·명령행·최종 보고에 저장하지 않는다.
- 서버 Agent 조회 결과는 하드웨어 ID와 Agent ID가 확정된 현재 작업 안에서 재사용한다. 등록 전 조회, 등록 후 검증, 준비 확인의 목적을 구분하고 같은 목록 API를 불필요하게 반복하지 않는다.
- 명령 stdout/stderr는 실행 중 작업 로그로 즉시 스트리밍하고 메모리에는 최근 200줄만 유지한다. 각 단계명, 상태, 이전 단계 이후 경과 시간, 전체 경과 시간과 장시간 명령 heartbeat를 통합 터미널에 표시한다. 최종 JSON만 기다리게 하지 않는다.
- 단계 성공 결과는 기존 내용을 덮어쓰지 않고 추가하는 실행 이력에 입력 식별값과 함께 남긴다. 같은 작업의 성공 단계는 입력이 같을 때 재실행하지 않는다. 다른 작업에서는 과거 원본·커버리지 빌드, 래퍼 처리, 산출물 생성·갱신 확인 결과를 재사용하지 않는다.
- 공통 `buildSummary`는 종료 시 이미 존재하는 로컬 단계 JSON만 조합한다. 보고를 위해 빌드·configure·Agent 조회·모델 판단을 추가하거나 완료 단계를 다시 실행하지 않는다.
- 별도 지정이 없으면 빌드 PC의 CPU 수를 기준으로 최대 8개의 병렬 작업을 사용한다. `COVER_BUILD_PARALLEL` 또는 실행기의 `--parallel` 값이 있으면 그 값을 우선한다.
- 고객 명령이나 CI가 병렬도를 명시하면 그대로 보존한다. 병렬 실행이 프로젝트 동작을 바꿀 수 있는 Maven/Gradle과 일부 임베디드 빌드는 근거 없이 새 병렬 옵션을 추가하지 않는다.

## 결정과 재개를 줄이는 방법

원본 빌드 전에 알 수 있는 값과, 실제 빌드가 끝나야 알 수 있는 값을 구분한다. 아직 실행하지 않은 빌드의 JDK나 산출물을 추측해서 결정 횟수를 줄이지 않는다.

1. 원본 빌드 전에는 언어·빌드 시스템·진입점·구성·task 등 현재 확인 가능한 미결정 항목을 `PREBUILD_DECISION_BUNDLE_REQUIRED`에 함께 제시한다. 고객 명령이 있으면 검증한 `originalBuildPlan`을 우선한다. 스크립트에서 명령 문자열을 발견했다는 사실만으로 task와 작업 디렉터리가 확정됐다고 판단하지 않는다.
2. Java 원본 빌드가 끝나면 로그에서 JDK 경로·버전과 JAR/WAR 경로를 함께 수집하고 설치된 JACOV 메타데이터와 대조한다. 자동으로 확정하지 못한 항목만 `JAVA_POSTBUILD_DECISION_BUNDLE_REQUIRED`에 묶는다.
   Maven은 `<modules>` 관계로 reactor 루트를 하나로 확정하고 `-V`의 `runtime:` 경로를 실제 JDK 후보로 사용한다. 이미 빌드 파일과 로그에 답이 있는 항목을 모델 결정으로 다시 보내지 않는다. goal은 프로젝트 파일만으로 알 수 없으므로 고객 명령이나 모델이 확정한 값을 유지한다.
3. 단일 Gradle 빌드 환경에서는 원본 빌드 전 결정 한 번과 후속 결정 한 번 이내를 목표로 한다. 값이 명확하면 해당 대기를 생략한다. 혼합 저장소나 고객 스크립트의 조건 분기로 새 정보가 드러난 경우에는 필요한 결정을 추가하되, 앞서 확정한 항목을 다시 질문하지 않는다.

재개 시 `choices` 전체를 모든 단계의 입력 식별값에 넣지 않는다. 예를 들어 JACOV 도구 선택을 추가했다고 원본 Gradle 빌드까지 다시 수행해서는 안 된다.

| 단계 | 재사용 여부를 판단하는 입력 |
| --- | --- |
| 프로젝트 조사·빌드 근거 수집 | 프로젝트 소스·빌드 파일 목록과 내용, 선택한 처리 환경 |
| 원본 Java 빌드 | 구조화된 원본 계획, 프로젝트 입력, 빌드 실행 파일 해시, 빌드에 영향을 주는 환경값의 해시 |
| JACOV 설치 조사 | 설치 파일 경로와 내용 해시 |
| 원본 Java 결과 해석 | 원본 로그 해시, 설치 파일, 산출물·JDK·JACOV 관련 선택값 |
| Maven 로컬 설치 | 설치 명령, 원본 JAR 해시, 저장소 경로와 현재 설치 JAR 해시 |
| 검증된 Java 계측 빌드 | 계측 명령, 소스 입력, JACOV·설정·init script 해시와 현재 산출물 해시 |

파일의 포함·제외 범위는 [project_index.py](../scripts/project_index.py)의 `SOURCE_SUFFIXES`, `BUILD_NAMES`, `BUILD_SUFFIXES`, `SKIP_DIRS`, `GENERATED_OUTPUT_DIRS`를 따른다. `.cover-build`, `.cover-ee`, `.git`과 생성 산출물 디렉터리를 소스 변경으로 취급하지 않는다. Java 원본 빌드의 환경 해시는 현재 `JAVA_HOME`, `PATH`, `GRADLE_USER_HOME`, `MAVEN_OPTS`, `JAVA_TOOL_OPTIONS`, `JDK_JAVA_OPTIONS`를 대상으로 한다. 고객 빌드가 별도의 외부 파일이나 다른 환경값에 의존한다면 이 목록만으로 모든 변경이 검출된다고 가정하지 않는다.

Java 계측까지 성공하고 재사용 설정 저장만 실패했다면, 같은 작업에서 입력과 계측 산출물 해시가 모두 유지된 경우에만 검증 결과를 이어 쓴다. 산출물이 삭제되거나 다른 빌드가 덮어쓴 경우에는 계측 빌드를 다시 수행한다. 다른 작업의 성공 기록에는 이 규칙을 적용하지 않는다.

`--no-environment-profile`을 지정하면 다른 작업의 환경 프로필을 읽지 않는다. 이 옵션을 사용해도 현재 작업 안의 입력 검증과 성공 단계 재사용은 유지한다.

인증 성공 JSON은 자격 증명이 아니다. 같은 프로세스에서는 메모리 인증을 재사용하지만 새 프로세스에서는 Access Key를 다시 안전하게 전달해야 한다. 서버 연결 가능 여부도 과거 JSON만 믿지 않고 계측 직전에 짧게 확인한다. 키 저장이나 오래된 연결 상태 재사용으로 이 확인을 없애지 않는다.

## Java의 clean 이전 확인과 복구

커버리지 `clean` 전에 JACOV 설정의 형식, JDK와 플러그인, init script의 절대 JAR 경로, 실행 명령을 확인하고 Open API 인증 및 JACOV 서버 TCP 연결 확인을 수행한다. TCP 연결 성공은 JACOV 인증이나 TLS 검증 성공을 뜻하지 않는다. 이 둘은 제품 계측 중의 실제 응답으로 확인한다. 상세 순서는 [Java 문서](java.md#clean-이전-확인)를 따른다.

현재 실행 환경의 정책이나 확인된 오류로 외부 연결이 제한된다는 근거가 있으면, Java 서버 연결 단계부터 허용된 실행 권한으로 시작한다. 승인 절차는 도구에서 처리한다. 샌드박스에서 `clean build`를 실패시킨 뒤 전체 작업을 반복하는 방식은 사용하지 않는다. 모든 호스트에서 샌드박스가 실패한다고 가정하거나 권한을 우회하지 않는다. 승인이 거부되면 사용자 대기로 종료한다.

계측 빌드 실패 후 예상 원본 산출물이 실제로 없어졌을 때에만 `recovery-original-java` 명령으로 복구한다. 사전 확인에서 중단됐거나 산출물이 그대로 있으면 복구 빌드를 실행하지 않는다. 복구 결과는 `recover-java-artifacts` 단계에 남기며, 복구 성공을 계측 성공으로 바꾸지 않는다. 다른 파이프라인의 파일 복구·Toolbox 해제·Agent 설정 복원 순서는 그대로 유지한다.

예상 산출물 중 하나라도 없으면 저장된 원본 명령 전체를 한 번 실행한다. `recovery-original-java`는 사용자가 따로 실행할 명령이 아니라 이 복구 로그의 이름이다. 파일이 모두 존재하면 손상 여부나 내용 변경만을 이유로 자동 복구 빌드를 시작하지 않는다. 이 경우 계측 검증의 실패 상태를 유지하며, 파일이 존재한다는 사실을 정상 산출물의 증거로 보고하지 않는다.

## 로그와 시간 기록

공통 명령 실행기는 `coverage-java.attempt-001.log`처럼 시도별 로그를 남긴다. 다음 시도는 번호를 증가시키며 이전 로그를 덮어쓰지 않는다. 단계 JSON은 실제 시도 로그를 가리킨다. 기존 파일명을 사용하는 도구를 위해 `coverage-java.log`는 마지막 시도의 복사본으로 유지한다. 원본 빌드와 복구 빌드는 서로 다른 이름을 사용한다.

파이프로 수집하는 출력은 비밀값을 가린 뒤 파일과 최근 출력 버퍼에 기록한다. JACOV 설정 파일에서는 검증에 필요한 key를 메모리로만 읽고 제품의 `Key:` 로그도 가린다. C# Toolbox의 네이티브 콘솔 실행 방식은 바꾸지 않는다. 이 모드는 stdout 캡처 대신 실행 상태 로그를 남기므로 파이프 출력과 같은 수집 방식이라고 설명하지 않는다.

시간 기록은 다음을 구분한다.

- 외부 명령: 시도별 `.metrics.json`에 UTC 시작·종료 시각, monotonic clock으로 측정한 `durationMs`, 종료 코드를 기록한다.
- 체크포인트 실행: 실제 작업 호출의 시작·종료와 소요 시간을 `timing.measurement=ACTION`으로 기록한다. 재사용은 `REUSED`와 실행 시간 0으로 구분한다.
- 그 밖의 기존 단계 기록: `SINCE_PREVIOUS_RECORD`는 이전 기록 이후의 구간이다. 이 값을 해당 함수만 실행한 시간으로 해석하지 않는다.
- 실행기 프로세스: `execution-times.json`에 호출별 시작·종료, 활성 시간, 프로세스 안의 자격 증명 입력 대기를 기록한다.
- 프로세스 사이의 대기: 직전 종료 상태가 `WAITING_MODEL`이면 모델 결정 대기 구간, `WAITING_USER`이면 사용자 대기 구간으로 집계한다. 이 구간에는 사람이 읽는 시간, 도구 승인, 재개 준비도 포함될 수 있다. 순수 모델 추론 시간을 측정했다고 표현하지 않는다.

`buildSummary.performance`에는 `totalDurationMs`, `activeDurationMs`, `externalWaitDurationMs`, `resumeCount`, `checkpointReuseCount`, `commandDurations`, `slowestStages`와 대기 종류별 합계만 넣는다. 이미 있는 이벤트와 명령 측정값으로 계산하며 성능 보고를 위해 빌드나 서버 요청을 추가하지 않는다. `activeDurationMs`에는 빌드·네트워크 시간도 포함되며 프로세스 안의 입력 대기는 제외한다. 강제 종료되어 호출 종료 기록이 없는 경우에는 마지막 호출의 전체 시간을 복원했다고 단정하지 않는다.

이전 실행과 비교할 때에는 단계 기록 수와 실제 실행 횟수를 구분한다. 데몬 준비 상태, 의존성 캐시, 서버 응답, 입력 대기가 다르면 전체 감소율을 실행기 코드만의 개선율로 보고하지 않는다.

정상 종료 기록이 모두 있는 작업에서 `totalDurationMs = activeDurationMs + externalWaitDurationMs`이다. `externalWaitDurationMs`에는 프로세스 사이의 재개 대기와 프로세스 안의 자격 증명 입력 대기를 모두 포함한다. 실행 방법과 결정 파일의 입력 형식은 [워크플로](workflow.md)와 [결정 파일 작성 규칙](decision-contract-v2.md)을 따른다.

## 실행 중인 Agent의 준비 상태 확인

- 새로 시작한 Agent는 현재 또는 회전된 `testmonitor*.log`의 reporting 초기화와 monitoring watch 시작 기록을 확인한다.
- 이미 실행 중인 Agent는 현재 `testmonitor.log`가 최근 15분 이내 갱신됐고 `ThreadWatchDog`에서 `AgentReportService`, `LogMonitor`가 살아 있으면 재사용 준비 증거로 인정한다.
- 서버 `online=true`, listener, 래퍼 매핑, 모니터링 경로 접근성도 함께 충족해야 한다. heartbeat만으로 다른 조건을 생략하지 않는다.
- 초기화 문구가 로그 파일 교체로 `testmonitor.1.log` 등에 이동한 경우 현재 파일에 같은 문구가 없다는 이유로 60초를 모두 기다리지 않는다.

## 환경별 적용

- Visual Studio: `Configuration|Platform`은 [Visual Studio 판정 기준](visual-studio.md#판정-기준)에 따라 선택한다. 기존 산출물의 경로·최신 수정 시각은 보조 근거이며, 이것만으로 구성을 자동 선택하지 않는다. 이미 확인한 구성은 공통 재사용 조건을 만족할 때 이어 쓴다.
- Visual Studio: 고객 스크립트·CI가 MSBuild를 지정하지 않았고 프로젝트의 `PlatformToolset`이 `v143`처럼 한 세대로 확정되면 정확히 대응하는 Visual Studio 설치 세대를 선택한다.

  이름이 가장 최신이라는 이유만으로 선택하지 않는다.
- Visual Studio/C#: 고객 MSBuild 병렬 설정이 없으면 `/m:<N>`을 사용한다. 실제 컴파일러 추출에 필요한 diagnostic 증거는 유지하되 같은 원본 빌드를 다시 수행하지 않는다.
- Visual Studio: 빌드 시스템·진입점·구성·MSBuild 선택이 끝나면 `VsDevCmd` 캡처, `TargetPath`, 원본·커버리지 MSBuild를 포함할 첫 실행기 호출을 도구 호출의 호스트 권한으로 시작한다. 접근 거부가 예상되는 샌드박스에서 시험 삼아 실행하지 않는다. 자격 증명을 이미 받았으면 `--prompt-credentials`를 같은 실행에 포함한다.
- CMake: 요청된 안전 정책을 유지한다. 원본 네이티브 configure와 커버리지 configure를 각각 수행하고 두 configure 사이의 캐시를 재사용하지 않는다. 이 항목은 속도를 이유로 축약하지 않는다.
- 직접 Make: 실제 커버리지 빌드를 먼저 수행한다. `make -n -B`는 래퍼 선택 실패를 진단하거나 명령을 출력하지 않는 recipe에서 원본 도구를 보조 확인할 때만 실행한다.
- STM32CubeIDE: 화면 없이 실행하는 IDE 내부 빌더의 기존 병렬 설정을 보존하고 별도 병렬 옵션을 추가하지 않는다. 원본과 커버리지에서 같은 프로젝트·빌드 구성을 사용하며 IDE 실행 파일 탐색과 프로젝트 import를 반복하지 않는다.
- C#: C# 프로젝트 조사는 한 번 수집하고 프레임워크·솔루션·프로젝트·Toolbox 입력을 함께 확정한다. 원본 빌드 전에 기존 Toolbox 설정을 `disable`하고, 실패 복구도 `disable`로 수행한다. Toolbox enable 결과와 CscHooker 실제 처리 증거는 같은 작업에서 재사용한다.
- Java: Maven/Gradle 진입점·JDK·goal·task·모듈·소스 묶음을 한 번에 계획한다. Maven `-T`나 Gradle `--parallel`은 고객 명령/CI/프로젝트 설정에 이미 있거나 사용자가 승인한 경우에만 보존·사용한다. Local Agent 설치본과 유효한 `cover_jacov.json`만 확인하고, Java 커버리지 빌드를 위해 Agent를 시작하지 않는다.

## 성능 개선에서도 유지할 검증

- 상세 로그(verbose/diagnostic)를 남기는 원본 빌드와 실제 컴파일러·링커·아카이버 또는 JDK 확인은 생략하지 않는다.
- 원본과 커버리지 산출물의 절대 경로 비교, 실제 wrapper/CscHooker/JACOV 처리는 생략하지 않는다.
- 성능을 이유로 고객 빌드 파일을 미리 수정하거나 PATH 전역 주입을 사용하지 않는다.
