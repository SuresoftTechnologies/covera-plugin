# 커버리지 빌드 워크플로

전체 흐름은 `필수 정보 확인 → 기존 COVER 적용 일시 해제 → 프로젝트 환경조사 → 환경조사 JSON 생성 → 원본 빌드 방법 확정 → 원본 빌드(verbose) → 실제 툴체인 확인 → Agent 준비 → 커버리지 빌드 → wrapper/계측 처리/산출물 검증 → 영속 적용 → 최종 자연어 요약` 순서다.

## 단계별 수행 내용과 기록

### 1. 입력 확인

AI Agent는 프로젝트 절대 경로, Local Agent 서버 URL, Local Agent 설치 경로와 COVER Open API 메인 웹 서버 URL을 확인한다. 먼저 `${CODESCROLL_TM_INSTALL_PATH}/agent_kit/open-api-credentials.json`에 유효한 URL·Access Key가 있는지 확인하고, 있으면 재사용해 다시 묻지 않는다. 없으면 최초 요청에 Access Key나 메인 웹 서버 URL이 없을 때 누락된 프로젝트 경로와 함께 채팅으로 요청하고 입력을 기다린다. URL은 절대 HTTP(S) 주소로 받으며 알려진 host나 포트를 추측하지 않는다. 입력을 받은 뒤 환경조사와 원본 빌드를 진행한다. 키는 현재 대화·인증 프로세스의 메모리에만 보관하며, 이 시점에는 서버를 호출하지 않는다.

평소 사용하는 원본 빌드 명령은 선택적으로 받는다.

> 평소 사용하는 원본 빌드 명령이나 스크립트가 있으면 알려주세요. 없다면 프로젝트 파일을 분석해 자동으로 찾겠습니다.

Visual Studio 사용자는 명령어 대신 `.sln` 또는 `.vcxproj`와 평소 사용하는 `Configuration|Platform`으로 답할 수 있다.

`.cover-ee/applied-state.json`이 있으면 이전에 적용한 COVER 설정을 원본 빌드 동안 일시 해제한다. COVER 설정이 남아 있으면 원본 빌드도 래퍼를 거칠 수 있기 때문이다.

- Visual Studio의 import, STM32CubeIDE의 도구 실행 명령과 Agent `gcc.config`, CMake/Make의 대체 처리에서 수정한 파일은 원본 백업으로 일시 복원한다.
- C# 설정은 Toolbox `disable`로 해제한다.
- Maven/Gradle의 수동 명령용 파일은 원본 빌드에 자동 적용되지 않으므로 복원 대상이 아니다.
- 작업이 대기·실패·중단되면 이전 COVER 적용 상태를 되살린다.
- 현재 파일의 해시가 기록된 적용 해시와 다르면 고객이 변경했을 수 있으므로 덮어쓰지 않는다.

### 2. 이전 조사 결과 확인과 빌드 대상 선택

이전 성공 작업의 환경 프로필을 현재 빌드 설정 파일, 요청 조건, 도구 식별 정보와 비교한다. 모두 일치하면 기존 프로젝트 파일 목록과 판정·선택 결과를 재사용한다.

일치하지 않으면 프로젝트 디렉터리를 한 번 순회해 `project-index.json`을 만든다. 네이티브, STM32CubeIDE, C#, Java 탐지기는 이 파일 목록을 함께 사용한다.

같은 작업의 재개에서는 관련 파일과 디렉터리별 목록의 변경 여부를 확인하고, 변화가 없으면 인덱스와 탐지 결과를 이어 쓴다. 입력 검증을 위한 파일 확인까지 생략하는 것은 아니다. 다른 작업 기록 사용을 금지한 실행은 `--no-environment-profile`을 지정한다. 현재 작업의 재개와 다른 작업의 환경 프로필은 [성능 문서](performance.md#결정과-재개를-줄이는-방법)에 따라 구분한다.

#### 혼합 저장소에서 한 작업이 처리하는 범위

C#/Java 소스, `.vcxproj`, CMake/Make 진입점이 함께 있으면 여러 빌드 환경이 섞인 후보로 기록한다. 후보를 함께 조사하는 것과 모든 환경을 계측하는 것은 구분한다. 한 작업(job)은 선택한 빌드 환경 하나만 처리한다.

- 저장소 전체의 대표 언어를 임의로 고르지 않는다. 사용자가 요청한 진입점·타깃과 의존 관계를 확인한다.
- 확인한 범위를 기준으로 `NATIVE`, `CSHARP`, `JAVA` 중 처리 대상과 사용할 빌드 시스템을 선택한다.
- 후보가 여러 개이면 모델이 빌드 파일과 고객 스크립트의 관계를 해석한다. 이 근거로도 대상을 정할 수 없을 때만 사용자에게 확인한다.
- 선택한 환경의 파이프라인으로 원본 빌드부터 계측·검증까지 진행한다. 같은 작업에서 다른 환경의 파이프라인을 차례로 호출하지 않는다.

한 환경을 선택한다는 것은 프로젝트를 하나로 제한한다는 뜻이 아니다. 선택한 솔루션의 여러 C/C++ 프로젝트나 Maven·Gradle의 여러 모듈은 해당 빌드 환경에서 함께 처리할 수 있다. 함께 빌드하고 검증할 프로젝트 묶음은 선택한 진입점·타깃과 환경별 판정 기준에 따라 정한다.

예를 들어 저장소에 CMake 네이티브 라이브러리와 Maven Java 애플리케이션이 함께 있어도, CMake 작업이 끝난 뒤 JACOV를 자동 실행하지 않는다. 두 환경 모두 계측해야 한다면 별도 빌드 작업으로 나누어 다룰 범위를 확인한다. 현재 작업의 성공을 다른 환경까지 검증한 결과로 보고하지 않는다.

### 3. 프로젝트 환경조사

빌드 진입점, 빌드 스크립트, CI, 프리셋, 캐시, 기존 빌드 로그, C#·Java 프로젝트와 배포 후보 파일의 경로·해시를 언어별 확인 근거에 기록한다.

배포 파일만으로 MSA를 단정하지 말고 비밀값과 환경변수 값은 기록하지 않는다.

### 4. 환경조사 JSON 생성과 계획 작성

사전 조사 결과를 `cover-environment-survey.json`에 기록한다. 빌드 계획은 사용자가 제공한 내용을 우선하고, 실행 파일·인자·작업 디렉터리·환경 초기화 항목으로 나누어 작성한다.

입력이 없으면 고객 스크립트/CI, 캐시·프리셋/기존 로그, 프로젝트 표준 명령, 모델의 파일 내용·관계 해석 순으로 계획을 만든다.

여러 언어가 섞인 솔루션, STM32CubeIDE, Java의 여러 모듈·소스 묶음처럼 수집된 파일만으로 관계를 확정할 수 없는 경우에만 모델이 증거와 빌드 파일을 해석한다.

이 순서로도 근거가 없을 때만 사용자에게 필요한 값만 요청한다.

원본 빌드 전 미결정 항목은 `PREBUILD_DECISION_BUNDLE_REQUIRED`로 함께 제시한다. 한 값을 고른 뒤 동일한 조사 결과를 다시 읽어 다음 값을 묻는 흐름을 만들지 않는다. Java의 실제 JDK·산출물처럼 원본 빌드 후 확인할 항목은 이때 추측하지 않고, 빌드 후에도 남은 항목만 `JAVA_POSTBUILD_DECISION_BUNDLE_REQUIRED`로 묶는다.

계획을 선택한 뒤 작업 디렉터리·환경 초기화·구조화 명령과 선택 근거를 조사서에 확정한다.

### 5. 계획 검증

실행 파일, 인자 배열, 작업 경로, 제한 시간, 환경변수 이름, 빌드 시스템과 계측 주입 전략을 검증한다.

검증되지 않은 셸 문자열은 실행하지 않는다.

### 6. 원본 빌드(verbose)

확정한 계획으로 원본 빌드를 실제 수행한다. 도구 경로와 산출물은 이 빌드의 로그에서 확인한다.

| 환경 | 원본 빌드에서 남기는 로그 |
| --- | --- |
| Visual Studio | MSBuild 진단 로그(diagnostic) |
| CMake | CMake 상세 빌드 로그(verbose) |
| Make | 실제 실행한 recipe, 즉 타깃을 만드는 명령 출력 |
| STM32CubeIDE | 화면 없이 실행하는 IDE 내부 빌더의 상세 로그 |
| C# | 진단 로그 또는 binlog |
| Maven·Gradle | 선택한 빌드 도구의 상세 로그 |

STM32CubeIDE는 선택한 프로젝트와 빌드 구성을 `-cleanBuild`로 빌드한다. IDE가 생성한 Makefile을 직접 호출하지 않는다.

산출물은 검증된 기존 프로젝트 경로에 만든다. 작업 기록 디렉터리에는 로그·계획·증거만 둔다.

이미 수행한 원본 빌드 한 번에서 다음 결과를 함께 수집해 `original-build-evidence.json`에 기록한다. 확인 결과는 종류를 구분해 저장하며, 기록을 위해 원본 빌드를 추가로 실행하지 않는다.

- 네이티브: 실제 도구가 수행한 컴파일·링크·아카이브 역할과 산출물
- C#: 컴파일러 실행 방식(`PROCESS_EXE`, `DOTNET_CSC_DLL`, `COMPILER_SERVER`, `IN_PROCESS`)과 산출물
- Java: 실제 JDK, 컴파일러 실행 방식과 산출물

Gradle은 원본 빌드에 관찰용 init script를 넣어 실제 컴파일러 metadata와 archive 경로를 기록한다. 고객 빌드 파일과 출력 경로는 변경하지 않는다. 같은 작업에 후속 결정만 추가됐고 원본 입력이 그대로이면 이미 성공한 원본 빌드를 반복하지 않는다.

### 7. 원본 빌드 후 인증과 서버 연결

원본 빌드와 실제 도구·산출물 확인이 끝난 뒤, 최초 대화에서 받은(또는 캐시 파일에서 읽은) Access Key를 첫 COVER 서버 작업 직전에 메모리 세션으로 전달해 사용한다. Open API는 사용자가 알려준(또는 캐시 파일의) 메인 웹 서버 URL을 정규화한 HTTPS 원점으로 호출한다. Local Agent에는 `CODESCROLL_TM_SERVER_URL`을 그대로 사용한다. Open API v1만 호출하며, 키의 유효성과 권한은 첫 API 응답으로 확인한다. 이 첫 인증이 성공하면 두 값을 `${CODESCROLL_TM_INSTALL_PATH}/agent_kit/open-api-credentials.json`에 캐시해 다음 실행부터 재사용한다.

실행기의 키 확인은 최초 대화에서 입력을 받는 절차와 별개다. 실행기를 직접 호출하거나 작업 재개 중 키 전달이 누락된 경우에도, 키 없이 서버 작업을 진행하지 않도록 확인한다. 이때의 중단·재개는 아래 ‘실패와 대기’ 절을 따른다.

커버리지 빌드 요청 자체가 Open API에는 사용자가 알려준(또는 캐시 파일의) 메인 웹 서버 URL, Java 계측에는 `cover_jacov.json.url`을 사용하여 필요한 빌드·계측 정보를 전송하는 것을 허용하므로 별도 전송 승인을 묻지 않는다. `CODESCROLL_TM_SERVER_URL`은 Local Agent의 remote-service 연결에만 사용한다. 각 주소는 역할이 다르므로 원점이 같아야 한다고 판단하지 않는다.

C/C++·STM32CubeIDE·C#은 제품이 만든 하드웨어 ID로 `GET /v1/agent`를 조회하고, 없을 때만 `POST /v1/agent`로 등록한다.

네이티브 도구의 기존 매핑은 변경하지 않고 재사용한다. 매핑이 없는 도구에만 호환 ToolChainInfo를 선택하고 `PATCH /v1/agent`로 추가한다. STM32CubeIDE에서 호환 정의가 없으면 지정된 파서 템플릿으로 새 정의를 생성한다. 다른 환경에서는 정의를 준비할 때까지 사용자 입력을 기다린다. 생성 조건과 공유 정의의 수정 제한은 [Open API 요청과 Agent 설정](security-and-api.md#open-api-요청과-agent-설정)을 따른다.

Java는 유효한 `cover_jacov.json`을 사용하고 Local Agent를 시작하지 않는다. Open API 주소와 JACOV 주소가 다르다는 이유만으로 중단하지 않는다.

### 8. 계측 준비

C/C++은 실제 툴체인 래퍼, C#은 실제 `csc.exe`를 담은 Toolbox 입력, Java는 설치 파일의 메타데이터와 현재 JDK/소스 호환 수준을 근거로 선택한 JACOV CLI/plugin을 준비한다.

JACOV 파일명과 JDK 주 버전만으로 호환성을 자동 확정하지 않는다.

관련 없는 C/C++ ToolChainInfo를 C#/Java 때문에 만들지 않는다.

### 9. 실행 준비 확인

Agent 조회와 분리된 준비 단계에서 C/C++·STM32CubeIDE는 빌드 요청 수신 포트·reporting·서버 `online=true`·래퍼 동기화·모니터링 파일 감시 서비스를, C#은 C# 빌드 서비스 9092·reporting·서버 `online=true`를 확인한다.

필요한 경우 Agent DTO의 래퍼 매핑과 실제 `toolchaininfo`도 이 단계에서 검증한다.

이 단계가 통과하기 전에는 커버리지 빌드를 시작하지 않는다.

Java 커버리지 빌드는 JACOV의 COVER 서버 직접 연결과 분석정보 업로드를 확인하며 Local Agent online 상태를 요구하지 않는다.

Java 런타임 listener 9091은 표준 `tm-javalib` 측정 실행을 요청했을 때만 확인한다.

조회 증거와 실행 준비 증거는 서로 다른 단계 JSON으로 남긴다.

### 10. 커버리지 빌드

C/C++ 래퍼, C# Toolbox/CscHooker, Java JACOV CLI/Maven/Gradle 중 선택된 주입만 사용한다.

CMake/Make는 환경별 주입 정책을 적용한다.

STM32CubeIDE는 원본 빌드와 같은 IDE 내부 빌더를 화면 없이 호출한다. 같은 프로젝트·빌드 구성에 `-Ep PATH=<wrapper>`를 추가하고, 선택 빌드 구성이 네이티브 도구 실행 명령을 절대 경로로 고정한 경우에만 프로젝트 `.cproject`를 백업·최소 변경한 뒤 한 번의 `-cleanBuild`를 수행한다.

실패하면 변경한 설정을 복구한다. 성공하면 검증한 설정으로 13단계 ‘설정 유지와 재사용’을 진행한다.

실제 빌드의 상세 로그에서 래퍼 적용을 검증하며 SDK·IDE 설치 파일은 자동 수정하지 않는다.

### 11. 호출 검증

네이티브는 실제 래퍼 역할, C#은 선택된 각 `.csproj`의 Toolbox 구조·래퍼 실행 명령·CscHooker 실행을 확인한다.

Java Maven/Gradle은 설치본이 출력한 `JAVA SOURCE COVERAGE BUILD RESULTS` 집계 또는 JACOV 실행 문맥에 속한 `.java` 파일별 `[SUCCESS]`/`[FAILURE]`/`[IGNORE]` 결과를 확인한다.

Java는 계측 성공이 1건 이상이고 계측 실패·생략·오류가 없어야 한다. 파일별 `[IGNORE]`는 제외 결과로 기록하며, 제외가 있다는 이유만으로 실패 처리하지 않는다. `Skipping jacov instrumentation`처럼 JACOV 계측 자체를 건너뛴 로그와 일반 테스트 생략은 구분한다. 구체적인 문구와 판정 예시는 [Java의 JACOV 처리 결과 확인](java.md#jacov-처리-결과-확인)을 따른다.

제품명 문자열이나 출처가 불명확한 success 한 줄로 성공 처리하지 않는다. JACOV 처리가 확인돼도 다음 단계에서 빌드 산출물을 별도로 검증한다.

### 12. 산출물 검증

빌드 전후 크기·수정 시각·해시를 비교하고, 원본 상세 로그에서 기록한 절대 산출물 경로와 커버리지 로그에서 독립 관찰하거나 현재 빌드 구간에 실제 갱신된 산출물 경로를 비교한다.

원본 목록을 자기 자신과 비교하지 않는다.

`sameAsOriginal=true`가 아니면 `COVERAGE_OUTPUT_PATH_CHANGED`로 중단한다.

### 13. 설정 유지와 재사용

검증한 커버리지 설정을 이후 IDE나 수동 명령에서도 사용할 수 있도록 남긴다. 임시 설정은 작업 기록 디렉터리 밖으로 옮기고, 재사용 설정과 명령에서 작업별 임시 경로를 제거한다.

**Visual Studio와 C#**

- Visual Studio는 선택한 `.vcxproj`의 검증된 `Configuration|Platform`에만 props 연결을 적용한다.
- props는 `.cover-ee/config/cover-msbuild.props`에 두고, 같은 label의 기존 COVER import는 경로·구성·위치를 검증한 뒤 현재 import 하나로 교체한다.
- `/p:ForceImportBeforeCppTargets`와 `/p:CoverWrapperDirectory`를 제거한 같은 Rebuild에서 래퍼 호출과 동일 경로 신규 산출물을 다시 확인한다. 실패하면 프로젝트 연결을 복구하고 `APPLIED`로 기록하지 않는다.
- C#은 Toolbox enable 상태를 유지한다.

**STM32CubeIDE**

- `.cproject`에서 선택한 빌드 구성 ID를 찾는다.
- `.settings/org.eclipse.cdt.core.prefs`의 해당 구성에 래퍼 경로를 맨 앞에 둔 `PATH`와 `COVER_BR_CONFIG=gcc.config`를 적용한다.
- 도구 절대 경로를 바꾸는 대체 처리를 사용했다면 `.cproject` 변경도 유지한다.
- 성공한 검증용 설정을 Agent `gcc.config`에 적용한다.
- 새 workspace에서 `-Ep`와 프로세스 `PATH`/`COVER_BR_CONFIG` 주입 없이 `-cleanBuild`를 다시 수행한다. IDE에 저장한 설정만으로 래퍼 호출과 신규 산출물이 확인돼야 한다.
- 이 검증이 실패하면 프로젝트 설정과 Agent 설정을 복구하며 `APPLIED`로 기록하지 않는다.
- 프로젝트 설정과 원본 `gcc.config`는 프로젝트 `.cover-ee/backup`에 보관한다. Agent 원본은 원래 파일 옆의 `.cover-ee-backup`에도 보관한다.
- 검증용 Agent 설정 파일은 성공·실패 모두 삭제한다.

**CMake와 Make**

- 명령행 주입이 성공하면 프로젝트 파일을 바꾸지 않고 검증된 재실행 명령을 남긴다.
- 명령행 주입이 실패해 프로젝트 파일 수정으로 성공한 경우에만, 각 원본과 같은 폴더에 `.cover-ee-backup` 원본과 수정본을 유지한다.

**Maven과 Gradle**

- Maven은 플러그인이 설치된 재사용 로컬 저장소와 JACOV `setup` goal 명령을 남긴다. POM은 수정하지 않는다.
- Gradle은 플러그인 JAR와 init script를 프로젝트 루트에 두고 `--init-script` 명령을 남긴다. `settings.gradle[.kts]`와 `build.gradle[.kts]`은 수정하지 않는다.

`.cover-ee/applied-state.json`에는 적용 해시, 원본 백업, 빌드 방식, 산출물, 수동 실행 진입점을 기록한다. 비밀값은 넣지 않는다.

### 14. 공통 빌드 기록과 최종 자연어 요약

조사서, 원본 빌드 증거와 단계별 JSON에서 빌드 시스템·실제 커버리지 명령·선택 타깃·계측 처리·산출물을 모아 `workflow-state.json`의 `result.buildSummary`에 작성한다.

Visual Studio, GCC/CMake/Make, STM32CubeIDE, C#, Java에 [build-reporting.md](build-reporting.md)의 같은 형식을 사용한다.

성공 채팅에는 `프로젝트 환경 및 빌드 파악`, `커버리지 빌드 적용`, `파일 변경`을 독립된 제목으로 반드시 표시하고, 파일 변경은 `persistentSetup.fileChanges`의 수정·생성·백업 경로를 근거로 설명한다.

그 뒤 산출물, 이후 IDE 또는 수동 빌드 방법과 로그를 정리한다.

최종 보고용 환경조사 JSON을 새로 만들거나 사전 조사서를 갱신하지 않는다.

### 15. 선택적 측정 검증

사용자가 요청했을 때만 검증된 실행 명령으로 계측 코드를 실행하고 런타임 연결과 서버 측 결과 갱신을 별도로 판정한다.

각 단계의 최신 호환 결과는 현재 작업의 `.cover-build/jobs/<jobId>/stages`에, 기존 기록에 추가하는 실행 이력과 입력 식별값은 `events`에 기록하고 공통 요약은 `workflow-state.json`의 `result.buildSummary`에 둔다.

재개할 때는 같은 `job.json`을 사용하고 입력 식별값이 같은 성공 단계만 재사용하며, 다른 작업의 결과·승인·결정을 가져오지 않는다.

## 수행 시간 원칙

- 로컬 환경조사에서 언어·빌드 시스템·진입점·구성·타깃 후보를 함께 수집하고, 모델 결정이 필요하면 한 묶음으로 처리한다.
- 같은 작업을 재개하면 입력 식별값이 같은 성공 단계의 증거를 재사용한다. 관련 빌드 파일이나 선택 근거가 변경된 단계부터만 다시 수행한다.
- Visual Studio/MSBuild는 빌드 시스템·진입점·`Configuration|Platform`·MSBuild가 확정된 뒤, `VsDevCmd` 캡처나 MSBuild 평가에 도달하는 첫 실행부터 호스트 권한과 PTY로 호출한다. Access Key를 이미 받았다면 `--prompt-credentials`로 원본 빌드 뒤 Open API Agent 준비와 커버리지 빌드를 같은 실행기 프로세스에서 끝낸다.
- 인증 입력 보완이나 예상하지 못한 권한 실패로 같은 작업을 재개하더라도, 원본 계획·선택 빌드 입력의 내용·소스 입력이 같으면 성공한 원본 빌드 체크포인트를 재사용한다. 이후 빌드에 유지하는 COVER 연결을 동일 바이트로 해제·복원하면서 바뀐 파일 수정 시각만으로 원본 빌드를 다시 실행하지 않는다.
- 최초 대화에서 받은 Access Key는 첫 서버 작업 전까지 대화·인증 프로세스 메모리에만 보관한다. Agent는 macAddress로 직접 조회하며 환경별 분기에서 Access Key를 다시 요청하지 않는다.
- 명령 출력은 작업 로그에 즉시 스트리밍하고 프로세스 메모리에는 최근 일부만 유지한다. 단계가 끝날 때마다 통합 터미널에 단계명·상태·구간 시간·누적 시간을 출력하고 장시간 명령에는 heartbeat를 표시한다.
- 기본 병렬도는 CPU 수 기준 최대 8이며 명시된 고객 값이 우선이다. Maven/Gradle처럼 병렬 실행이 task 의미를 바꿀 수 있으면 고객 근거 없이 새 옵션을 추가하지 않는다.
- 이미 실행 중인 Agent는 최신 watchdog 생존 확인 기록과 회전 로그를 함께 확인해 준비 상태를 판정한다.
- 직접 Make의 실행 예정 명령 목록은 실제 래퍼 선택 실패 또는 명령을 출력하지 않는 원본 recipe의 보조 확인 때만 수행한다.
- CMake 네이티브 configure와 커버리지 configure는 계속 분리한다. 캐시를 재사용해 이 두 configure를 합치는 최적화는 적용하지 않는다.

## 역할 분리

공통 실행기는 상태, 성공 단계 기록, 인증, 증거, 복구와 보고를 담당한다. 환경별 어댑터는 해당 환경에 필요한 실행 순서와 계측 확인 방법을 담당한다.

네이티브 래퍼, C# Toolbox, Java JACOV에 같은 단계 목록을 강제하지 않는다. Local Agent 실행, 툴체인 매핑, 프로젝트 파일 변경, JACOV key의 필요 여부를 환경별로 구분한다. 필요 없는 단계를 `no-op`으로 채우지 않는다.

### 스크립트·모델·사용자 판단의 구분

전체 작업은 모델이 진행한다. 아래 값은 전체 작업의 지휘자가 바뀐다는 뜻이 아니라, 개별 선택을 어떤 근거로 확정하는지 나타낸다.

| 구분 | 언제 사용하는가 |
| --- | --- |
| `SCRIPT` | 정형 규칙으로 후보가 하나로 결정돼 추가 해석 없이 계획을 만들 수 있다. |
| `MODEL` | 후보가 여럿이거나 조건부 관계가 있어 모델이 파일 관계와 고객 절차를 해석해야 한다. |
| `USER` | 저장소와 로그에 고객의 실제 선택 의도가 없어 사용자 확인이 필요하다. |

모델은 후보를 환경 이름만으로 미리 축약하지 않는다. 각 후보의 진입점, 빌드 타깃, 구성, 명령 근거, 산출물, 선택에 영향을 주는 옵션을 하나의 빌드 방법으로 묶어 비교한다.

### 처리 구성요소별 역할

- 증거 수집기는 파일·설정·로그에서 사실을 기록한다. 고객 빌드 명령을 추측하지 않는다.
- 모델 플래너는 수집한 근거와 빌드 파일을 해석해 구조화된 계획과 선택 이유를 작성한다.
- 계획 검증기는 허용된 경로·명령·환경·주입 전략만 실행기로 전달한다.
- 실행기는 계획대로 명령을 수행하고 실행 시각·로그·프로세스 결과를 기록한다.
- 사후 검증기는 실제 계측 처리와 신규 산출물을 독립적으로 확인한다.

## 실패와 대기

C/C++ 커버리지 빌드 로그에 `excluded from coverage build(analysis error)` 또는 `excluded from coverage build(analysis error - multi)`가 있으면 AI Agent는 [빌드 스킬의 분석 오류 복구 절차](../SKILL.md#cc-분석-오류가-발생한-경우)에 따라 같은 플러그인의 복구 스킬을 수행한다. 종료 코드가 0이어도 확인하며, 정상 제외인 `(option)`과 구분한다. `ReadyForRebuild` 이후에는 복구된 서버 연결을 유지한 채 같은 빌드 작업을 재개하고 실제 재빌드·산출물 검증까지 마친다. 복구가 끝나기 전에 실행기의 `FAILED`를 전체 작업의 최종 결과로 단정하지 않는다.

- `--execute` 없이 실행하면 계획을 확인한 뒤 실행 전 대기한다. 이 상태에서는 재사용 설정을 적용하거나 커버리지 빌드 성공 결과를 만들지 않는다.
- 실행기 종료 코드는 `0=SUCCEEDED`, `1=FAILED`, `2=WAITING_MODEL`, `3=WAITING_USER`로 구분한다. 대기 상태를 성공 종료로 해석하지 않는다.
- 정형 규칙만으로 단일 계획을 만들 수 없으면 `WAITING_MODEL`로 두고 모델이 증거의 의미를 해석한다.
- 저장소·스크립트·로그에도 선택 근거가 없어 모델이 고객 의도를 확인할 수 없으면 `WAITING_USER`로 전환한다. 질문에는 모델이 정리한 실제 후보와 각 후보의 근거·산출물·핵심 차이를 포함하고, 사용자가 평소 명령·타깃·프로젝트·모듈·산출물 중 익숙한 값으로 선택할 수 있게 한다.

  파일과 로그에서 이미 확인한 정보를 사용자에게 다시 입력하게 하지 않는다. 예를 들어 STM32CubeIDE의 프로젝트명은 `.project`에서, 빌드 구성 후보는 `.cproject`에서 확인한다. 고객 스크립트·CI·기존 로그로도 실제 사용 대상을 정할 수 없을 때만, 남은 프로젝트나 빌드 구성 후보를 제시해 선택을 요청한다.
- 고객 빌드 설정이 없어 계획을 만들 수 없으면 `WAITING_USER`로 둔다.
- AI Agent는 캐시 파일에 유효한 값이 없으면 최초 대화에서 Access Key와 Open API 메인 웹 서버 URL 입력을 기다린다. URL이 없으면 실행기도 `OPEN_API_MAIN_WEB_SERVER_URL_REQUIRED`와 `WAITING_USER`(종료 코드 3)를 반환하며 새 작업을 만들거나 서버 연결을 시도하지 않는다. `CODESCROLL_TM_SERVER_URL`로 대신 채우지 않고 사용자에게 받은 주소를 `--open-api-server-url`로 전달해 새 작업을 시작한다. 이와 별개로, 실행기를 직접 호출하거나 작업 재개 중 키가 실행기 프로세스에 전달되지 않은 경우에는 원본 빌드 후 첫 COVER 서버 작업 직전의 확인에서 `AUTHENTICATION_INPUT_REQUIRED`를 기록하고 `WAITING_USER`로 중단한다.
- 키 전달이 누락된 작업은 같은 `job.json`으로 재개한다. 현재 대화에서 이미 받은 키가 있으면 다시 요청하지 않고 전달한다. 받은 키가 없을 때만 사용자에게 입력을 요청한다. 입력이 같은 성공 단계는 기존 재사용 규칙을 따른다.
- 원본 빌드 실패와 COVER 빌드 실패를 분리해 보고한다.

## 범위와 완료 기준

이 스킬은 한 번의 계측 빌드뿐 아니라 이후 빌드에서 사용할 설정까지 남긴다. 따라서 커버리지 빌드가 성공했는지와 스킬 작업이 끝났는지를 나누어 판단한다.

- **커버리지 빌드 성공**: 빌드가 오류 없이 끝나고, 해당 환경의 실제 계측 처리와 원본 산출물과 동일한 절대 경로의 신규 산출물을 확인한 상태다. 11·12단계와 환경별 성공 판정 기준을 모두 충족해야 한다.
- **스킬 작업 완료**: 커버리지 빌드 성공 후 13단계의 재사용 설정 적용을 마치고, 14단계의 작업 결과와 이후 IDE·수동 빌드 방법까지 사용자에게 안내한 상태다. 설정 파일이나 보조 스크립트를 생성했다는 사실만으로 완료 처리하지 않는다.

예를 들어 계측 빌드와 산출물 검증은 통과했지만 재사용 설정을 적용하지 못했다면, 커버리지 빌드 결과는 확인된 사실대로 설명하되 전체 작업은 미완료로 보고한다. 설정 적용 실패 원인과 복구 결과도 함께 남긴다. 성공한 빌드 결과를 전체 작업 성공으로 바꾸어 기록하지 않는다.

실제 실행에서 Python 실행기는 `persistent_setup.publish()`가 끝난 뒤 전체 성공 결과를 기록한다. 최종 채팅의 수동 빌드 안내는 AI Agent가 수행한다. 위 구분은 보고할 범위를 명확히 하기 위한 것으로, 기존 상태값이나 환경별 검증 순서를 바꾸지 않는다.

테스트/프로그램 실행, 서버 Module 조회, 측정 데이터 확인은 사용자가 요청했을 때 이 스킬의 선택 단계로 수행한다. 커버리지 빌드 성공이나 기본 스킬 작업 완료 조건에는 포함하지 않으며, 결과를 별도로 보고한다. 장비 배포, CVD 업로드, 커버리지 결과 계산은 별도 요청과 별도 스킬에서 처리한다.
